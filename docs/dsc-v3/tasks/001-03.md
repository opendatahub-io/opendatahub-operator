# DSC-V3-001-03: Migrate production code to typed v3

## Lifecycle and scope

Read the authoritative local documents, `001.md`, and `001-01.md` Outcomes.
Update metadata and Outcomes before code and use Modern Go guidance. This work
may run in parallel with DSC-V3-001-02 after the v3 API is stable. Preserve
runtime behavior because the v2 and v3 schemas are identical. Do not change a
component contract, default, validation, lifecycle rule, or internal resource
identity.

## Indicative starting files

In addition to the controller and handler directories below, inspect and migrate
these easily missed typed-v2 or v2-GVK consumers with their adjacent tests:

- `pkg/cluster/resources.go` and `pkg/cluster/resources_test.go`;
- `pkg/initialinstall/creation.go`;
- `pkg/upgrade/uninstallation.go` and `uninstallation_test.go`;
- `pkg/controller/predicates/resources/resources.go` and `resources_test.go`;
- `pkg/controller/actions/deploy/action_deploy_support.go` and
  `action_deploy_support_test.go`, plus typed DSC fixtures in
  `action_deploy_test.go`;
- `pkg/utils/test/mocks/types.go` and `pkg/utils/test/scheme/scheme.go`;
- `internal/controller/modules/types.go`, `base.go`,
  `modules_controller_actions.go`, their tests, and every component/module
  handler returned by the v2 import search; and
- `tests/e2e/helper_test.go`, `test_context_test.go`, `controller_test.go`, and
  `resilience_test.go` for current-runtime factories, schemes, and component
  reflection.

Do not mechanically migrate explicit v2 conversion/admission/compatibility
fixtures. Classify every remaining search hit and record the final allowlist.

## Required migration

Replace typed v2 DSC usage with typed v3 in:

- `internal/controller/datasciencecluster` reconciliation, actions, status,
  and tests;
- `internal/controller/components/registry` and every in-tree component
  handler signature, fixture, and test;
- `internal/controller/modules` context, interfaces, base handler, reflection,
  lifecycle/readiness/status aggregation, module registry, every module
  handler, and their tests;
- predicates, initial-install helpers, status utilities, runtime upgrade
  helpers, generators, E2E factories, and other production consumers; and
- samples/fixtures whose purpose is current production behavior rather than v2
  compatibility.

Use existing repository/framework abstractions; do not introduce a generic
reflection layer merely to reduce mechanical edits. Preserve error behavior,
status semantics, owner references, release handling, and action ordering.
Garbage collection must remain the final action in every touched chain.

## Compatibility boundary

After migration, typed v2 imports are allowed only for v2 conversion,
version-specific v2 admission, explicit compatibility/upgrade tests, and the
independent v2 schema baseline. Produce an exact remaining-hit allowlist from:

```bash
rg -n 'datasciencecluster/v2|dscv2' api cmd internal pkg tests -g '*.go'
```

Do not remove v1 in this subtask; DSC-V3-001-02 owns that atomic deletion.
This subtask must not edit versioned API directories, admission/conversion
webhooks, GVK definitions, `pkg/dsc/compare`, or CRD/conversion patches; those
belong to DSC-V3-001-02. This subtask only removes typed-v2 production usage.

## Tests and definition of done

Update tests alongside every migrated package. Prove reconciliation, component
and module lifecycle, status aggregation, predicates, initial install,
generators, and helpers behave unchanged on typed v3 objects. Run focused
package tests plus all mandatory Make gates. Complete when production uses only
typed v3 DSC objects, the v2 allowlist is minimal and recorded, GC remains last,
and no opportunistic behavior change is present.
