# DSC-V3-007: Implement the Dashboard projection

## Lifecycle and scope

Read `../development.md`, `../decisions.md`, `../PLAN.md`, `../TASKS.md`,
`002.md`, `005.md`, and the `006.md` Outcomes. Update metadata and Outcomes on
start. Implement only the accepted Dashboard contract. Internal Dashboard CR
identity and unrelated modules are out of scope. Use Modern Go guidance and
preserve GC as the final action in every touched action chain.

## Existing behavior to preserve

`internal/controller/modules/dashboard/handler.go` currently enables the shared
Dashboard operator when core Dashboard or MaaS Consumer Portal is managed. It
projects component maps, applications/notebooks/model-registry namespaces, and
gateway domain into the existing module CR, then mirrors portal readiness and
status. V2 behavior must remain observable through v2/v3 conversion.

The accepted public v3 contract is defined by DEC-027:

- `spec.components.dashboard.standard.managementState` is the core Dashboard.
- `spec.components.dashboard.maasPortal.managementState` is the independently
  managed MaaS Consumer Portal.
- The parent `dashboard` is structural; both children are independently
  Managed or Removed, and empty is effectively Removed.
- The existing internal Dashboard CR projection remains: the core state maps
  to the CR's existing `managementState`, while the portal maps directly to
  `spec.maasConsumerPortal.managementState`.
- Existing Dashboard and portal status fields and
  `MaaSConsumerPortalAvailable` condition behavior remain unchanged.

The wire mapping is explicit: v2 `dashboard.managementState` becomes v3
`dashboard.standard.managementState`; v2
`dashboard.maasConsumerPortal.managementState` becomes v3
`dashboard.maasPortal.managementState`. Reverse conversion restores those v2
paths. The nine combinations of `Managed`, `Removed`, and empty for the two
independent v3 children are covered; empty behaves as Removed at runtime.

## Implementation

1. Consume the accepted version-owned v3 Dashboard fields produced by
   DSC-V3-006; use `standard` and `maasPortal`, do not reintroduce provisional
   names, and do not mutate v2 shared types.
2. Update `internal/controller/modules/dashboard` projection and module
   enablement for every accepted core/portal state combination.
3. Preserve existing namespace, component-map, gateway-domain, release, owner,
   and management annotation behavior unless the accepted contract explicitly
   changes it.
4. Map the accepted source conditions to the exact DSC v3 status and condition
   names, including removed/unavailable children and readiness aggregation.
5. Update module schema inputs only when the accepted projection requires it;
   do not rename internal CR/GVK/module metadata.
6. Keep v2 Dashboard and portal behavior compatible through the central
   converter. This task must not edit public v2/v3 types, conversion methods,
   the OpenAPI inventory/baseline, or central generated DSC artifacts. If the
   accepted handler cannot be implemented without such a change, reopen a
   serialized DSC-V3-006 follow-up that applies DEC-003/DEC-007 and completes
   before this task resumes.
