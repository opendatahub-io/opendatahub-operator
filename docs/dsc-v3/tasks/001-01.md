# DSC-V3-001-01: Establish the baseline and introduce v3

## Lifecycle and scope

Read `../development.md`, `../decisions.md`, `../PLAN.md`, `../TASKS.md`, and
`001.md`. On start, update status, dates, assignee, and Outcomes. Before every
Go edit, apply the Modern Go guidance required by `development.md`. Record new
durable decisions in `../decisions.md` before relying on them.

This subtask introduces v3 with exactly the existing v2 wire contract. It must
not add any proposed Dashboard, AI Hub, Data, MaaS, Training Operator, or Llama
Stack contract change.

## Indicative starting files

- Copy and independently compare `api/datasciencecluster/v2/datasciencecluster_types.go`,
  `groupversion_info.go`, and `zz_generated.deepcopy.go` when creating
  `api/datasciencecluster/v3`; do not make the v2 source itself the mutable
  expected side of the schema guard.
- Register/generate through `PROJECT`, `cmd/main.go`,
  `cmd/component-codegen/cmd/generator/generator.go`, and
  `pkg/utils/test/scheme/scheme.go`.
- Treat `api/datasciencecluster/v2/init_resource_annotation_test.go`, platform
  samples, CSVs, storage markers, converters, and webhook registration as
  handoff inputs. Their final cutover belongs to 001-02/001-04.
- Begin with these files and follow local dependencies. Run the v1/v2 searches
  from `../PLAN.md` as completion checks, and record any additional central
  scheme, fixture, or generator file they reveal in Outcomes.

## Implementation

1. Capture generated ODH and RHOAI DSC CRDs before changing the API.
2. Save an independent normalized v2 OpenAPI baseline suitable for later
   v2/v3 comparison. A v3 type or shared-type edit must not silently regenerate
   the expected v2 side.
3. Inventory v1/v2 API imports, GVK constants, schemes, PROJECT metadata,
   webhooks, code generation, samples, fixtures, bundles, and tests. Record the
   inventory location in Outcomes.
4. Add `api/datasciencecluster/v3` with version-owned DSC/list, group
   registration, spec, components, status, markers, defaults, validations,
   deprecated fields, printer columns, JSON names, and optionality identical to
   v2.
5. Add v3 without moving `+kubebuilder:storageversion` or `conversion.Hub` from
   v2. V2 remains the hub/storage version until DSC-V3-001-02 can atomically
   switch hub/storage and add the v2 spoke conversion. Do not remove v1.
6. Register v3 in `PROJECT`, `cmd/main.go`, test schemes, object factories, and
   version-aware helpers needed for API generation.
7. Point component-codegen and new primary DSC fixtures/samples at v3 where
   they do not depend on conversion/runtime migration.
8. Generate v3 deepcopy/object code and both platform CRD inputs.

## Tests and checks

- Test v3 group/version registration, object/list deepcopy, and generated
  schema markers. Version-specific defaulting, validation, warning, and
  admission registration/tests belong to DSC-V3-001-02 with the atomic cutover.
- Compare normalized generated v2 and v3 OpenAPI and require zero differences
  at this stage.
- Assert v2 remains the temporary hub/storage version and the new v3 types,
  scheme registration, and generated schema compile without changing current
  v1 -> v2 conversion behavior.
- Run focused API/generation tests and the mandatory generation, format, lint,
  unit, build, and diff checks from `development.md`.

## Definition of done

V3 compiles and generates as a schema-identical, version-owned API while v2
remains the temporary hub/storage version; the v2 baseline is independently
protected; no component contract change is present; all generated diffs and
evidence are recorded. The atomic hub/storage switch remains for
DSC-V3-001-02 and production migration for DSC-V3-001-03.
