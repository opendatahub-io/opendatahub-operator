## Objective

Freeze the v3 Data grouping and the v2 compatibility contract for Feature Store
and Data Registry. This is a decision task; implementation belongs to
DSC-V3-006 and DSC-V3-009.

## Current and proposed shapes

V2 exposes Feast lifecycle state and the approved compatibility Data Registry
child:

```yaml
components:
  feastoperator:
    managementState: Managed
    dataRegistry:
      managementState: Managed
```

The approved v3 shape is:

```yaml
components:
  data:
    featureStore:
      managementState: Managed
    dataRegistry:
      managementState: Managed
```

`data` is structural and has no parent management state; the children are
independent. Empty or absent management state is effectively `Removed`.
DEC-012 excludes Data Connection Hub, and DEC-011 keeps the internal
Data/Feast CR, GVK, and module metadata unchanged for 3.6.

The existing Feast module is enabled from `feastoperator.managementState`.
Its internal CR currently projects external-OIDC issuer configuration but no
Feature Store/Data Registry child lifecycle.

## Accepted decision

The resolved [RHOAIENG-95339](https://redhat.atlassian.net/browse/RHOAIENG-95339)
contract establishes:

- `data` is structural with independent `featureStore` and `dataRegistry`
  children and no parent `managementState`.
- V2 uses `feastoperator.managementState` and the explicit compatibility field
  `feastoperator.dataRegistry.managementState`.
- Both fields map directly and bidirectionally to the corresponding v3 Data
  children. No annotation stash is required.
- Empty or absent management state is effectively `Removed`.
- DCH and internal Data/Feast resource or metadata renames are excluded from
  the RHOAI 3.6 contract.
- Existing Feast status/runtime behavior is preserved; child runtime
  projection is separate implementation work.
