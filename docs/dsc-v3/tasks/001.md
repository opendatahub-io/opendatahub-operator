## Objective

Introduce the versioning machinery independently of unresolved component
contracts:

- add v3 with the current v2 wire schema unchanged;
- make v3 the conversion hub, storage version, and production-internal type;
- retain v2 as a served compatibility spoke with no-op semantic conversion;
- migrate production code from typed v2 to typed v3;
- remove the v1 API, v1 conversion, v1 admissions, and v1 generated serving;
- update unit, integration, and E2E coverage; and
- establish guards requiring conversion and tests for every later v3 change.

Dashboard, AI Hub, Data, MaaS, Training Operator, and Llama Stack transformations
are explicitly out of scope. They begin only after their accepted decisions are
recorded.

## Current state

- `api/datasciencecluster/v2` is the storage API and implements
  `conversion.Hub`.
- `api/datasciencecluster/v1` is the conversion spoke and owns the current
  controller-runtime `/convert` registration.
- `internal/webhook/datasciencecluster/v2/register.go` registers v2 admission
  handlers but does not currently register conversion.
- Production controllers, component registries, module interfaces/status
  writers, helpers, tests, and component-codegen use typed v2 objects.
- `pkg/cluster/gvk/gvk.go` has a global DSC GVK pointing at v2; the v2 validator
  compares requests to that global value.
- Generated ODH/RHOAI CRDs serve v1/v2 and store v2.
- Conversion patches currently list `conversionReviewVersions: [v1, v2]`; this
  is a Kubernetes protocol list and must become `[v1]`.
- `pkg/dsc/compare/v2only.go` compares only v1/v2 component field names and is
  not sufficient for v2/v3 OpenAPI conversion coverage.
- `conversion.opendatahub.io/aigateway-state` exists to preserve v2 state
  through the v1 converter.
- `go.mod` specifies Go 1.26.5.

## Implementation

### 1. Capture the baseline

- Generate or verify current ODH and RHOAI CRDs before changing types.
- Save a normalized v2 OpenAPI schema golden/baseline used by the structural
  conversion guard. It must be independent from v3 generation so a shared Go
  type change cannot update both sides silently.
- Inventory v1/v2 imports, version constants, registrations, generated files,
  tests, and samples with `rg` and record any intentionally retained v2 usage.
- Confirm whether the v1 conversion annotation has consumers outside the v1
  converter before planning its deletion.

### 2. Introduce v3 without changing the wire contract

- Add `api/datasciencecluster/v3` with version-owned DSC/list, spec, components,
  status, and group registration.
- Reproduce v2 fields, JSON tags, markers, defaults, validations, status,
  deprecated fields, and printer columns exactly.
- Do not edit shared `api/components/v1alpha1` types to create v3 behavior.
  Shared types referenced initially are frozen for this task. A future stanza
  change must introduce a v3-owned DSC-facing type and preserve the v2 OpenAPI
  baseline.
- During 001-01, leave `+kubebuilder:storageversion` and `conversion.Hub` on
  v2. In 001-02, move them to v3 atomically with v2 conversion activation and
  v1 deletion; never leave a compiling boundary with v3 hub and no v2 spoke.
- Register v3 in `PROJECT`, `cmd/main.go`, test schemes, object factories, and
  version-aware helpers.
- Point `cmd/component-codegen/cmd/generator/generator.go` at the v3 DSC type.
- Generate v3 deepcopy/object code.

### 3. Implement and register identity v2 <-> v3 conversion

- Implement explicit typed `ConvertTo` and `ConvertFrom` methods on v2 against
  the v3 hub. Do not use `unsafe` or JSON serialization.
- Copy object metadata, spec, and status without renames, drops, defaults,
  validation, normalization, or cluster calls. The expected target
  `TypeMeta`/GVK is the only semantic difference.
- Before deleting v1 webhook registration, register the controller-runtime
  conversion webhook using the v2 `conversion.Convertible` type.
- Delete the v1 API/converter in the same compiling change that moves the hub
  because the current v1 converter asserts v2 implements `conversion.Hub`.
- Introduce distinct `DataScienceClusterV2` and `DataScienceClusterV3` GVK
  constants. Make v2 and v3 admissions validate their own request versions.
- Generate `conversionReviewVersions: [v1]`. Do not add DSC versions `v2` or
  `v3` to that protocol field.

### 4. Migrate production code to typed v3

Update all production consumers, including:

- `internal/controller/datasciencecluster` reconciliation and status;
- `internal/controller/components/registry` and every in-tree handler;
- `internal/controller/modules` context, interfaces, base handler,
  lifecycle/readiness/status code, and every module handler;
- predicates, status helpers, initial-install helpers, comparison utilities,
  upgrade helpers, code generators, and E2E object factories; and
- tests/fixtures associated with each migrated package.

Behavior must remain unchanged because v2 and v3 have the same schema. Keep
garbage collection last in every action chain.

After migration, v2 imports are allowed only in conversion, v2 admissions, and
explicit compatibility tests. Record the final allowlist in Outcomes.

### 5. Establish future conversion coverage

- Replace/adapt the v1/v2-only comparison with a guard over normalized,
  generated v2 and v3 OpenAPI schemas.
- Compare paths, types, requiredness, nullability, defaults, enums, CEL rules,
  and list/map semantics. The expected difference set for this task is empty.
- Make future intentional differences machine-readable and pair each with
  direct `v2 -> v3`, direct `v3 -> v2`, and both round-trip test cases.
- Require stable `case_id` links in the shared test registry and fail the guard
  unless the runner executes all four conversion categories for every entry.
- Keep the independent v2 schema baseline protected from shared-type changes.

### 6. Remove v1 and hand off upgrade gating

The development-branch end state is v1-free. Task 1 removes v1 from the new
operator and generated artifacts. It does not implement or qualify odh-cli.
DEC-009 defines the future gate owned by DSC-V3-010 that must run before these
artifacts are promoted or installed as an upgrade.

#### Release handoff to DSC-V3-010

- The gate runs before OLM applies the new CRD, while the old v1/v2 operator
  and its conversion webhook are healthy.
- It reads the installed CRD and `status.storedVersions`. Mutation-free success
  is allowed only when v1 is already absent. If no DSC exists but v1 is listed,
  it must still remove v1 from CRD status and verify the result.
- If v1 is recorded and the singleton DSC exists, it reads and updates the
  object through v2 without changing spec, status, or metadata, then verifies
  the storage rewrite. The storage-version marker alone is not proof.
- Only after successful verification does it patch the CRD status subresource
  to remove v1 from `status.storedVersions`, read the status back, and require
  v1 to be absent.
- Unsupported source state, conversion or webhook failure, conflict exhaustion,
  incomplete verification, or status-update failure blocks the upgrade. Every
  partially completed state must be safe to retry.
- OLM may install the v1-free v2/v3 CRD only after this gate succeeds.
- After the new v2 <-> v3 webhook is healthy, the upgrade flow updates the DSC
  through v3, verifies v3 storage, and removes v2 from `status.storedVersions`
  only after no object remains stored as v2. V2 remains served and deprecated.
- Before the post-upgrade v3 rewrite, rollback to the old v1/v2 release is
  supported. Afterwards, rollback requires a tested v3 -> v2 down-migration;
  otherwise it must be reported and blocked as unsupported.

The bullets above are requirements for DSC-V3-010, not implementation or test
work for Task 1. Task 1 records the handoff and the v1-free artifact inputs.

- Remove `api/datasciencecluster/v1` and the v1 <-> v2 converter/tests.
- Remove v1 scheme/`PROJECT` entries, admission handlers, webhook registration,
  envtest wiring, GVK constants, compare code, fixtures, and samples.
- Delete `conversion.opendatahub.io/aigateway-state` only if no consumer remains.
- Remove v1 from ODH/RHOAI CRDs, bundles/CSVs, webhooks, and API docs.
- Adapt behavioral tests to v3 or v2 compatibility instead of deleting useful
  coverage merely because it was located under a v1 package.
- Preserve a historical unstructured fixture only if it already has another
  repository consumer. DSC-V3-010 owns any new odh-cli-specific fixtures;
  compiled v1 API/conversion code remains out of the final end state.

### 7. Regenerate delivered artifacts

- Regenerate ODH and RHOAI CRDs, webhook manifests/patches, RBAC if changed,
  bundles/CSVs, deepcopy/object code, API docs, and samples.
- Primary samples use
  `apiVersion: datasciencecluster.opendatahub.io/v3` while preserving the v2
  component shape.
- Final generated CRD assertions:
  - v2 is served, not storage, marked deprecated, and uses DEC-019's exact
    warning literal;
  - v3 is served and is the only storage version;
  - v1 is absent;
  - `/convert` is configured; and
  - `conversionReviewVersions` is exactly `[v1]`.

## Test matrix

### Unit

- Direct v2 -> v3 equality for fully populated metadata/spec/status.
- Direct v3 -> v2 equality for fully populated metadata/spec/status.
- Both whole-object round trips and repeated-conversion idempotence.
- Empty, `Managed`, `Removed`, optional, deprecated, status/condition, release,
  related-object, label, annotation, owner-reference, and finalizer values.
- Structural OpenAPI comparison with an empty expected-difference set.
- Separate v2/v3 GVK and admission request checks.
- Existing controller, handler, module, status, predicate, initial-install, and
  comparison behavior after migration to typed v3.

### Integration/envtest

- Submit real Kubernetes `ConversionReview` requests to `/convert` for v2 -> v3
  and v3 -> v2, with one and multiple objects.
- Create/read/update the same DSC through v2 and v3 while storage is v3.
- Verify status-subresource conversion and metadata preservation.
- Verify v2 and v3 defaulting/validation independently.
- Assert generated served/storage versions and ConversionReview protocol.

### Final E2E handoff

- Fresh install exposes v2/v3, stores v3, and does not expose v1.
- A v2 client can create, read, and update the v3-stored singleton DSC without
  data loss.
- Run both ODH and RHOAI variants.
