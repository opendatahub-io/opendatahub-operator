# DSC-V3-012: Migrate KServe MaaS configuration

## Lifecycle and authority

Read `../development.md`, `../decisions.md`, `../PLAN.md`, `../TASKS.md`, and
the completed DSC-V3-001 Outcomes. On start, set `status: in_progress`,
`start_date`, `assignee`, and `last_updated`, and populate Execution Outcomes.
On completion, record results, set `status: completed`, and set `end_date` and
`last_updated`.

DEC-022's forward precedence and accepted DEC-024's literal-marker/admission
contract are the conversion authority; DEC-024 supersedes DEC-022's reverse
policy and specifies the accepted normalization. DEC-023 defines the
integration-first test boundary. No component Jira resolution or additional product feedback is an
entry condition. If code reality conflicts with the accepted decisions,
record a new proposed decision and stop only the conflicting part; do not
silently choose different conversion behavior.

## Objective

Remove deprecated `spec.components.kserve.modelsAsService` from the v3 wire
schema and make `spec.components.aigateway.modelsAsAService` the only v3 MaaS
configuration. Keep the v2 API shape unchanged and served, remove the custom
MaaS field deprecation warnings, retain its existing update validation unless a
separate accepted decision changes it, and move existing runtime fallback
semantics into deterministic v2 <-> v3 conversion.

This task changes KServe/MaaS conversion,
reserved-annotation admission, custom field warnings, and the runtime fallback
made obsolete by conversion. KServe lifecycle, all other KServe fields,
AI Gateway Batch Gateway behavior, MaaS status, and condition names remain
unchanged.

There is no supported installed intermediate-v3 release exposing the old
KServe MaaS field. Do not add compatibility machinery for that development-only
shape; supported legacy sources enter through v2. Task 010's upgrade gates are
unchanged. Implementation and verification evidence are recorded below.

## Accepted conversion contract

### V2 to v3

1. Copy every KServe and AI Gateway field except the removed v3 KServe
   `modelsAsService` field.
2. Select v3 `aigateway.modelsAsAService.managementState` from the API-visible
   v2 values. The canonical MaaS field defaults to `Removed`, so an omitted
   canonical field is observed as `Removed` during admission and is not a
   separate public migration state. Canonical `Managed` is preserved. Legacy
   `Managed` selects canonical `Managed` only when the KServe parent is also
   `Managed`; an empty or `Removed` KServe parent gates legacy `Managed` off.
   All other combinations select canonical `Removed`.
3. Copy `aigateway.managementState` unchanged, except when the existing runtime
   fallback would enable AI Gateway: if it is empty while both
   `kserve.managementState` and legacy
   `kserve.modelsAsService.managementState` are `Managed`, set v3
   `aigateway.managementState` to `Managed`.
4. Ignore the incoming `conversion.opendatahub.io/maas-v2-state` annotation.
   Set its value to the literal `legacy-managed` whenever legacy v2 MaaS is
   `Managed` and canonical v2 MaaS is not `Managed`; otherwise remove it. The
   marker records where the legacy intent came from, including when a
   `Removed` or empty KServe parent prevents that intent from enabling
   canonical MaaS. The marker does not override the KServe parent gate.

The MaaS-state selection is equivalent to this table. `C` is the API-visible
v2 `aigateway.modelsAsAService.managementState`, `K` is the v2 KServe parent,
and `L` is deprecated v2 `kserve.modelsAsService.managementState`. An omitted
canonical field is represented as `Removed` because that is its API default.

| C | K | L | v3 canonical MaaS state | v3 marker | Reason |
| --- | --- | --- | --- | --- | --- |
| `Removed` | `Managed` | `Managed` | `Managed` | `legacy-managed` | Legacy MaaS is effective through the enabled KServe parent. |
| `Removed` | `Removed` or empty | `Managed` | `Removed` | `legacy-managed` | The KServe parent gates legacy MaaS off; intent remains recoverable. |
| `Removed` | any | `Removed` | `Removed` | absent | Both API-visible MaaS states are disabled. |
| `Managed` | any | any | `Managed` | absent | Explicit canonical `Managed` wins; no legacy marker is needed. |

Evaluate both MaaS states from the original v2 source object. Do not base one
decision on fields already mutated by another conversion step.

For example, this v2 object preserves the legacy intent without enabling
canonical MaaS because KServe is disabled. The canonical `Removed` value is
shown explicitly because it is the API default when that stanza is omitted:

```yaml
spec:
  components:
    kserve:
      managementState: Removed
      modelsAsService:
        managementState: Managed
    aigateway:
      modelsAsAService:
        managementState: Removed
```

Its v3 representation keeps canonical MaaS at `Removed` and adds only
`conversion.opendatahub.io/maas-v2-state: legacy-managed`. A v2 object with the
same legacy MaaS field and `kserve.managementState: Managed` instead projects
canonical MaaS to `Managed` and adds the same marker.

### Handler behavior that conversion must preserve

The current AI Gateway handler makes three related decisions. Treat these
outputs as the behavioral oracle for every v2 input row:

| Handler output | Current rule |
| --- | --- |
| AI Gateway CR `spec.modelsAsAService.managementState` | Use the selected canonical v3 MaaS state; legacy `Managed` selects `Managed` only when KServe is `Managed`. |
| MaaS submodule readiness/status enabled | Enabled only when canonical v3 MaaS is `Managed`. |
| AI Gateway platform-module state | Preserve a non-empty AI Gateway parent; otherwise synthesize `Managed` only when KServe and legacy MaaS are both `Managed`, then treat every other empty result as `Removed`. |

The converted v3 object, processed by the canonical-only v3 handler, must
produce the same three outputs as the pre-change handler produces directly
from the v2-equivalent object. Canonical v3 MaaS preserves canonical v2
`Managed`; legacy v2 `Managed` selects canonical v3 `Managed` only when the
KServe parent is `Managed`. A legacy `Managed` value remains recoverable through
the marker even when the KServe parent gates effective MaaS off. The independent
empty AI Gateway parent may still be synthesized to `Managed` only when both
the KServe parent and legacy MaaS are `Managed`.

### V3 to v2

1. Accept only an absent marker or literal `legacy-managed`; reject every
   unknown marker value, including a present empty string.
2. Always copy the AI Gateway parent to v2. A parent synthesized as `Managed`
   remains `Managed`, allowing AI Gateway and Batch Gateway to remain enabled
   independently of MaaS.
3. When the marker is present, restore canonical MaaS (`C`) to `Removed` and
   deprecated `kserve.modelsAsService.managementState` (`L`) to `Managed`.
   When the marker is absent, copy current canonical MaaS and set `L` to
   `Removed`. No projection snapshot is stored or compared.
4. Keep the independent KServe parent unchanged and consume the reserved marker
   on the v2 output. Preserve unrelated fields and annotations. A subsequent
   forward conversion resets the marker from the current visible `C`/`L` pair.

### Existing v2 CEL contract

Keep the CEL transition validation attached to v2
`kserve.modelsAsService`. Warning removal must not weaken it:

| Operation or transition | Result |
| --- | --- |
| Create with legacy `Managed` | Allowed |
| `Managed -> Managed` | Allowed |
| `Managed -> Removed` | Allowed |
| `Removed -> Removed` | Allowed |
| `Removed -> Managed` | Rejected |

The deprecated v2 field accepts only `Managed` and `Removed`; `Unmanaged` is
not a valid management-state value. Its CEL rule permits cleanup from
`Managed` to `Removed` but never permits re-enabling `Managed` after the field
has reached `Removed`:

```cel
self.managementState != 'Managed' ||
  (has(oldSelf.managementState) && oldSelf.managementState == 'Managed')
```

The v3 schema has no legacy field, so it has no corresponding field-specific
CEL rule. The converter consumes existing legacy `Managed` values but does not
invoke or duplicate admission validation. A retained marker restores legacy
`Managed` for v2 reads and survives unrelated v3 updates. A v2-originated write
derives provenance from the visible v2 `C`/`L` pair: when canonical v2 MaaS is
already `Managed`, the marker is absent and legacy `L` is cleaned to `Removed`. After
marker retirement, reverse conversion returns legacy `Removed`; the existing
CEL rule then prevents a v2 client from re-enabling that deprecated path.

### Literal marker and admission lifecycle

DEC-024 uses only `conversion.opendatahub.io/maas-v2-state: legacy-managed`.
No JSON payload, versioned encoding, original-value stash, or projection
snapshot is required. Forward conversion resets this single bit of legacy
intent solely from the incoming v2 `C`/`L` pair.

On native v3 `CREATE`, strip supplied reserved metadata. On v3 `UPDATE`, a
change to canonical MaaS management state deletes the marker permanently,
including if later reverted. KServe and AI Gateway parent edits are unrelated
and preserve the marker. Otherwise use only the `OldObject` marker, regardless
of whether the new object supplies, changes, omits, or deletes it. An old object
without a marker cannot acquire one through a v3 update. Reject unknown
authoritative marker values. Unrelated edits preserve the old marker and
unrelated annotations.

### Accepted normalization and shared types

Reuse the existing `componentApi` AI Gateway and canonical value types in both
API versions. No canonical pointer and no duplicated v2/v3 AI Gateway wrappers
are permitted. Preserve existing OpenAPI defaults and validation, the v2
baseline, and shared/internal module schemas. Only the approved legacy v3
KServe removal changes OpenAPI.

On `v2 -> v3 -> v2`, an AI Gateway parent synthesized as `Managed` stays
projected. Without provenance, v2 canonical MaaS receives the current v3 value
and legacy MaaS is `Removed`. With `legacy-managed`, reverse conversion restores
canonical MaaS to `Removed` and legacy MaaS to `Managed`, even when the KServe
parent is `Removed` because the marker records intent rather than effective
enablement. Consequently, changing the KServe parent through v2 recalculates
canonical MaaS while leaving AI Gateway enabled for independent submodules such
as Batch Gateway. Required tests use explicit expected normalized fixtures for
these cases. Test the API-defaulted `Removed` states, canonical `Managed`, and
the KServe parent gate; absent canonical MaaS is covered only as the
pre-admission representation of the `Removed` default.

### Implemented behavior examples

The table shows the valid v2 MaaS combinations and the independent KServe
parent gate. `C` is canonical AI Gateway MaaS, `K` is the KServe parent, `L`
is deprecated KServe MaaS, and `A` is the AI Gateway parent. `M` means
`Managed` and `R` means `Removed`. API defaulting makes omitted `C` equivalent
to `R`. `A'` is `A`, except that an omitted `A` becomes `M` when both `K` and
`L` are `M`.

| v2 C | v2 K | v2 L | v3 C | v3 A | v3 marker | reverse v2 C | reverse v2 L | reverse v2 A |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `R` | `M` | `M` | `M` | `A'` | `legacy-managed` | `R` | `M` | `A'` |
| `R` | `R` or empty | `M` | `R` | `A'` | `legacy-managed` | `R` | `M` | `A'` |
| `R` | any | `R` | `R` | `A'` | absent | `R` | `R` | `A'` |
| `M` | any | any | `M` | `A'` | absent | `M` | `R` | `A'` |

Without the marker, reverse conversion writes the v3 value only to canonical
v2 MaaS and resets deprecated KServe MaaS to `Removed`. The marker preserves
the legacy `Managed` intent across unrelated v3 updates and prevents the
projected canonical `Managed` value from becoming a new explicit v2 source.

The parent transition is intentionally asymmetric:

| Step | KServe parent | AI Gateway parent | Canonical MaaS | Legacy MaaS | Marker |
| --- | --- | --- | --- | --- | --- |
| Create through v2 | `Managed` | omitted | `Removed` (default) | `Managed` | absent on input |
| Stored/read as v3 | `Managed` | `Managed` (synthesized) | `Managed` | unavailable | `legacy-managed` |
| Read through v2 | `Managed` | `Managed` | `Removed` | `Managed` | hidden from v2 output |
| Set KServe parent to `Removed` through v2 | `Removed` | `Managed` | `Removed` | `Managed` | absent on input |
| Stored/read as v3 again | `Removed` | `Managed` | `Removed` | unavailable | `legacy-managed` |

The final state disables MaaS but deliberately leaves the AI Gateway parent
`Managed`; AI Gateway and independent submodules such as Batch Gateway remain
enabled. Re-enabling the KServe parent through v2 makes legacy MaaS effective
again and projects canonical MaaS back to `Managed`.

| Subsequent write | Marker after admission/conversion | Legacy L on v2 read |
| --- | --- | --- |
| Native v3 create supplies a marker | stripped | `Removed` |
| Unrelated v3 spec, metadata, or parent edit | restored from old v3 object | `Managed` if old marker was present |
| V3 status-subresource update | unchanged in storage | `Managed` if marker was present |
| V3 changes canonical MaaS state | cleared permanently | `Removed` |
| V3 later reverts that state | remains absent | `Removed` |
| V2 changes legacy `Managed` to `Removed` | reset from current v2 C/L; absent | `Removed` |
| V2 read-modify-write of marked `C=Removed`, `L=Managed` | recreated from visible C/L | `Managed` |
| V2 explicitly writes `C=Managed`, `L=Managed` | absent | `Removed` |
| V2 status-subresource update | unchanged in storage | `Managed` if marker was present |

For example, start with a v2 DSC whose KServe parent and legacy MaaS are
`Managed` and whose canonical MaaS is `Removed`. V3 selects canonical `Managed`
and stores the `legacy-managed` marker; a v2 read still shows legacy `Managed`.
Change canonical MaaS to `Removed` through v3: admission clears the marker,
and v2 now reads legacy `Removed`. Changing canonical MaaS back to `Managed`
does not restore the marker. The v2 CEL rule then rejects an attempt to set
legacy MaaS back to `Managed`.
