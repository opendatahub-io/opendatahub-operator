## Objective

Registry API while preserving the existing internal module identity.

## Existing behavior and resolved contract

- V2 uses `components.modelregistry`, DSC status `modelregistry`, and condition
  `ModelRegistryReady`.
- The accepted public v3 field is `components.aiHub`; `hub` and
  `modelregistry` are not v3 public names.
- The v3 namespace field is `applicationNamespace`; v2 retains
  `registriesNamespace` for compatibility.
- V2 defaults an empty managed `registriesNamespace` to
  `odh-model-registries` or `rhoai-model-registries`, depending on the build,
  and keeps the namespace immutable while managed.
- The handler projects v3 `applicationNamespace` to internal
  `instancesNamespace`, falling back to the applications namespace when empty,
  and mirrors the namespace into legacy DSC status.
- DEC-011 requires the internal GVK `AIHub`, resource `default-aihub`, module
  and manifest name `modelregistry`, and related metadata to stay unchanged in
  3.6.

Accepted shape (DEC-025 and DEC-028):

```yaml
components:
  aiHub:
    managementState: Managed
    applicationNamespace: model-registry
```

## Recorded decision

DEC-025 and DEC-028 record:

1. Public v3 spec/status paths `components.aiHub` and `status.components.aiHub`,
   with v3 namespace field `applicationNamespace` and condition `AIHubReady`.
2. Namespace optionality and behavior for absent, empty, defaulted, and custom
   values for both ODH and RHOAI builds.
3. Existing defaulting, fallback, validation, immutability, and update behavior
   in `Managed` and `Removed` states.
4. Field-by-field v2 -> v3 and v3 -> v2 mappings for spec, status, and
   `ModelRegistryReady` <-> `AIHubReady` conditions, including
   `registriesNamespace` <-> `applicationNamespace`.
5. V2 read-modify-write preservation and direct/round-trip conversion coverage.
